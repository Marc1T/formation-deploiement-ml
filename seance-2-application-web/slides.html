Partie 2

FastAPI : servir le modèle

Un contrat validé, une documentation gratuite, des tests sans serveur.

FastAPI

Pourquoi FastAPI

Validation

Les schémas Pydantic vérifient types et bornes. Une requête mal formée reçoit un 422 explicite sans toucher au modèle.

Documentation

/docs est générée automatiquement : vos camarades testent l'API depuis le navigateur, sans écrire une ligne.

Rapide et standard

uvicorn, ASGI, type hints : le même modèle que les grands frameworks, en 40 lignes.

FastAPI · projet fil rouge

Le squelette

from contextlib import asynccontextmanager
from fastapi import FastAPI, HTTPException
from api.schemas import PatientFeatures, PredictionOut
from diabetes_ml.predict import Predictor

state = {"predictor": None}
@asynccontextmanager
async def lifespan(app: FastAPI):
    state["predictor"] = Predictor("models/model.joblib")   # chargé UNE fois, au démarrage
    yield
app = FastAPI(title="API Risque de diabète", lifespan=lifespan)

@app.get("/health")
def health():
    return {"status": "ok" if state["predictor"] else "degraded"}

@app.post("/predict", response_model=PredictionOut)
def predict(patient: PatientFeatures):
    if state["predictor"] is None:
        raise HTTPException(503, "Modèle non chargé")
    return state["predictor"].predict_one(patient.model_dump())

FastAPI · projet fil rouge

Le contrat d'entrée

from pydantic import BaseModel, Field

class PatientFeatures(BaseModel):
    pregnancies: int = Field(ge=0, le=20)
    glucose: float = Field(ge=0, le=300, description="Glycémie à 2 h (mg/dL)")
    blood_pressure: float = Field(ge=0, le=200)
    skin_thickness: float = Field(ge=0, le=100)
    insulin: float = Field(ge=0, le=900)
    bmi: float = Field(ge=0, le=80)
    diabetes_pedigree: float = Field(ge=0, le=3)
    age: int = Field(ge=1, le=120)

class PredictionOut(BaseModel):
    prediction: int
    probability: float
    risk_level: str

Les bornes arrêtent les valeurs absurdes (âge négatif, glycémie à 5 000) avant le modèle.

response_model filtre et documente la sortie : un champ en trop est retiré, un champ manquant est une erreur.

Ce n'est pas de la validation métier : le modèle acceptera un patient de 2 ans avec 15 grossesses.

from fastapi.testclient import TestClient

def test_predict(client):
    r = client.post("/predict", json=PATIENT)
    assert r.status_code == 200
    assert r.json()["prediction"] in (0, 1)

def test_validation(client):
    r = client.post("/predict", json={**PATIENT, "age": -3})
    assert r.status_code == 422

def test_missing_model_returns_503(model_dir):
    app = load_app(str(model_dir / "absent.joblib"))
    with TestClient(app) as c:
        assert c.get("/health").json()["status"] == "degraded"
        assert c.post("/predict", json=PATIENT).status_code == 503

FastAPI

Configurer par l'environnement

from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", extra="ignore")
    model_path: str = "models/model.joblib"
    threshold: float = 0.5
    cors_origins: list[str] = ["*"]

Tout ce qui change d'un environnement à l'autre vient de variables d'environnement, jamais du code.

OùComment

Streamlit : une interface en Python

Des widgets, un appel à l'API, un résultat lisible.

Streamlit

Le principe

import httpx, streamlit as st
API_URL = os.getenv("API_URL", "")
st.title("Estimation du risque de diabète")

col1, col2 = st.columns(2)
glucose = col1.slider("Glycémie (mg/dL)", 40, 250, 120, key="glucose")

@st.cache_resource
def load_predictor():
    return Predictor(os.getenv("MODEL_PATH", "models/model.joblib"))

if st.button("Estimer le risque", type="primary"):
    if API_URL:
        result = httpx.post(f"{API_URL}/predict", json=features, timeout=20).json()
    else:
        result = load_predictor().predict_one(features)
    st.metric("Probabilité estimée", f"{result['probability']:.0%}")

Le script se réexécute à chaque interaction. Tout ce qui coûte (charger un modèle) va dans @st.cache_resource.

Le mode (local ou API) est de la configuration : API_URL vide ou non. Même application sur Streamlit Cloud et derrière Azure.

Un try/except autour de l'appel réseau : l'API peut être arrêtée, lente, ou répondre 503.

Partie 4

Docker : emballer pour que ça tourne partout

Une image, un conteneur, deux étapes, plusieurs services.

Docker

« Ça marche chez moi »

uv sync garantit les mêmes bibliothèques Python. Mais pas :

la même version de Python système

les mêmes bibliothèques C (BLAS, OpenSSL…)

le même système d'exploitation

Image

Un paquet figé qui contient le système, Python, les bibliothèques, votre code et votre modèle. Se construit avec un Dockerfile.

Conteneur

Une image en cours d'exécution, isolée. Le serveur cloud n'a besoin que de Docker.

Docker

Une image en deux étapes

Docker · projet fil rouge

Le Dockerfile

FROM ghcr.io/astral-sh/uv:0.9.17-python3.11-bookworm-slim AS builder
ENV UV_COMPILE_BYTECODE=1 UV_LINK_MODE=copy UV_PYTHON_DOWNLOADS=0
WORKDIR /app
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-install-project --no-default-groups --group api
COPY README.md ./
COPY src ./src
RUN uv sync --frozen --no-editable --no-default-groups --group api
COPY models ./models

FROM python:3.11-slim-bookworm AS runtime
WORKDIR /app
RUN useradd --create-home --uid 1000 appuser
COPY --from=builder --chown=appuser:appuser /app/.venv /app/.venv
COPY --from=builder --chown=appuser:appuser /app/models /app/models
COPY --chown=appuser:appuser api ./api
ENV PATH="/app/.venv/bin:$PATH" MODEL_PATH=/app/models/model.joblib PORT=8000
USER appuser
CMD ["sh", "-c", "uvicorn api.main:app --host 0.0.0.0 --port ${PORT}"]

Docker

Pourquoi ces choix

ChoixRaison
Deux étapes builder / runtimeL'image finale ne contient ni uv, ni cache, ni sources : plus petite, moins de surface d'attaque
COPY pyproject.toml uv.lock avant le codeLes dépendances ne se réinstallent pas quand seul le code change (cache de couches)
--no-default-groups --group apiL'API n'embarque ni Streamlit ni MLflow
USER appuserUn conteneur ne tourne pas en root
${PORT}Cloud Run et d'autres plateformes imposent le port par cette variable
COPY modelsOn déploie un artefact figé, pas un entraînement au démarrage

Docker

Les commandes

$ uv run dvc repro # le modèle doit exister
$ docker build -f docker/api.Dockerfile -t diabetes-api .
[+] Building 48.2s … => exporting to image => naming to docker.io/library/diabetes-api
$ docker run --rm -p 8000:8000 diabetes-api # port 8000 publié
$ docker ps # conteneurs en cours
$ docker logs <id> # les journaux
$ docker exec -it <id> sh # un shell dans le conteneur
$ docker image ls # les images et leur taille

.dockerignore exclut .venv, .git, mlruns, les tests : le contexte envoyé à Docker reste petit.

Docker Compose

Plusieurs services ensemble

services:
  api:
    build: { context: ., dockerfile: docker/api.Dockerfile }
    ports: ["8000:8000"]
  app:
    build: { context: ., dockerfile: docker/app.Dockerfile }
    ports: ["8501:8501"]
    environment:
      API_URL: http://api:8000
    depends_on: [api]
docker compose up --build
docker compose logs -f api
docker compose down

Dans le réseau interne, api est un nom DNS. Les ports publiés rendent les services visibles depuis votre navigateur.

Intégration continue avec GitHub Actions

Un robot rejoue lint, tests, entraînement et construction à chaque push.

Intégration continue

L'idée

Une machine neuve

Ubuntu, rien d'installé : si ça ne marche que chez vous, la CI le dit.

Une étape échoue

Les suivantes ne s'exécutent pas, vous êtes prévenu, la croix rouge est visible sur la pull request.

Un artefact

L'image publiée dans ghcr.io est exactement ce que le cloud déploiera.

Intégration continue · projet fil rouge

Le workflow

name: CI
on:
  push: { branches: [main] }
  pull_request:

jobs:
  qualite:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v6
      - run: uv sync --frozen
      - run: uv run ruff check . && uv run ruff format --check .
      - run: uv run pytest

  image:
    needs: qualite
    if: github.event_name != 'pull_request'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v6
      - run: uv sync --frozen && uv run dvc repro
      - uses: docker/login-action@v3
        with: { registry: ghcr.io, username: ${{ github.actor }}, password: ${{ secrets.GITHUB_TOKEN }} }
      - uses: docker/build-push-action@v6
        with: { context: ., file: docker/api.Dockerfile, push: true, tags: ghcr.io/${{ github.repository }}/api:latest }

Intégration continue

Ce qu'il faut voir

uv sync --frozen : la CI installe exactement uv.lock. Lock pas à jour → échec, au lieu de résoudre autre chose en silence.

needs: qualite : pas d'image si les tests échouent.

dvc repro dans la CI : le modèle est régénéré par le pipeline, donc toujours cohérent avec le code. Avec un remote DVC, on ferait dvc pull.

ghcr.io/<vous>/<depot>/api:latest : GitHub Container Registry, gratuit, authentifié par le jeton automatique. C'est l'image que la séance 3 déploiera.
