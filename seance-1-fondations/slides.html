Introduction

Pourquoi déployer ?

Un modèle inutilisé ne vaut rien

Tant qu'il vit dans un notebook, seul son auteur peut s'en servir. La valeur apparaît quand quelqu'un d'autre peut poser une question et obtenir une réponse.

Reproductible ou perdu

« Ça marchait la semaine dernière » : sans versions figées, sans données versionnées, le résultat n'est pas reproductible, donc pas fiable.

Du code au service

Un service tourne sans vous : il démarre seul, répond à des requêtes, se met à jour. Cela demande une chaîne d'outils, pas un geste héroïque.

Git et GitHub en 20 minutes

Le minimum pour versionner le code et préparer l'intégration continue.

Git express

Git en cinq commandes

$ git init -b main
Initialized empty Git repository in ./diabete-lab/.git/
$ git status
Untracked files: pyproject.toml src/ README.md
$ git add .
$ git commit -m "Projet initial"
[main (root-commit) 3f2a1c9] Projet initial · 4 files changed
$ git log --oneline
3f2a1c9 Projet initial

Un commit est un instantané nommé de tout le projet. On y revient, on le compare, on le partage.

Git express

Publier sur GitHub et trois réflexes

git remote add origin https://github.com/<vous>/<depot>.git
git push -u origin main

Créez d'abord un dépôt vide sur github.com. Authentification : GitHub CLI (gh auth login) ou jeton d'accès.

Un .gitignore dès le début. .venv/, __pycache__/, .env, mlruns/, et les gros fichiers de données.

Des commits petits et nommés. « Ajoute l'étape prepare » vaut mieux que « maj ».

Jamais de secret dans Git. Une clé commitée est compromise, même supprimée au commit suivant.

Partie 3

uv : Python et dépendances reproductibles

Déclarer ce qu'on veut, figer ce qu'on a, exécuter au bon endroit.

uv

Le problème avec pip install

Aujourd'hui, chez vous

pip install pandas scikit-learn
# pandas 2.3.1, scikit-learn 1.7.2 … ou pas

Six mois plus tard, sur une autre machine : d'autres versions, une API qui a changé, un modèle qui ne se charge plus.

vs

Avec uv

uv add pandas scikit-learn
# écrit pyproject.toml ET uv.lock

Partout, toujours : uv sync réinstalle exactement les mêmes versions, jusqu'aux dépendances des dépendances.

Deux notions à séparer : ce que vous demandez (pandas ≥ 2.2) et ce qui est installé (pandas 2.3.1, numpy 2.2.6, …).

uv

Le cycle : déclarer, figer, installer, exécuter

ÉlémentRôleDans Git ?
pyproject.tomldéclare le projet et ses dépendancesoui
uv.lockfige toutes les versions résoluesoui
.python-versionversion de Python du projetoui
.venv/l'environnement installénon, régénéré par uv sync

uv

Les commandes

uv init mon-projet            # nouveau projet : pyproject.toml, .python-version, README
cd mon-projet
uv add pandas scikit-learn    # ajoute, résout, met à jour uv.lock, installe
uv add --dev pytest ruff      # dépendances de développement
uv add --group api fastapi    # dépendances dans un groupe nommé
uv remove pandas
uv sync                       # installe exactement uv.lock (crée .venv au besoin)
uv run python train.py        # exécute dans l'environnement, sans l'activer
uv run pytest
uv lock --upgrade-package pandas   # met à jour une dépendance, et seulement elle
uv python install 3.11        # installe un interpréteur
uvx ruff check .              # lance un outil sans l'ajouter au projet

uv run est la commande à retenir. Elle garantit la bonne version de Python et des bibliothèques, sur votre machine comme en CI ou dans Docker.

uv · projet fil rouge

Des groupes pour des images légères

[project]
dependencies = ["pandas>=2.2", "scikit-learn>=1.5", "joblib>=1.4", "pyyaml>=6.0"]

[dependency-groups]
api   = ["fastapi>=0.115", "uvicorn[standard]>=0.30", "pydantic-settings>=2.4"]
app   = ["streamlit>=1.38", "httpx>=0.27", "google-genai>=1.0"]
mlops = ["mlflow>=3.0", "dvc>=3.50"]
dev   = ["pytest>=8.3", "ruff>=0.6"]

[tool.uv]
default-groups = ["api", "app", "mlops", "dev"]

En développement

uv sync installe tout : confortable.

Dans Docker (séance 2)

uv sync --no-default-groups --group api : l'image de l'API n'embarque ni Streamlit ni MLflow.

Le cœur

Entraîner et prédire ne demandent que pandas et scikit-learn.

uv

Pièges fréquents

ModuleNotFoundError alors que c'est « installé » : vous avez lancé python au lieu de uv run python. Mauvais environnement.

uv.lock en conflit après un merge : uv lock le régénère proprement, puis commit.

uv sync recrée .venv quand la version de Python change : normal, et rapide grâce au cache.

error: Failed to build « Readme file does not exist » : pyproject.toml référence un README absent. Créez-le.

Partie 4

DVC : versionner les données et le pipeline

Git pour le code, DVC pour tout ce qui est lourd ou régénéré.

DVC

Pourquoi pas Git pour les données ?

Ko

Git est fait pour du texte : il stocke chaque version, calcule des diffs lisibles.

Go

Un CSV de 500 Mo ou un modèle de 2 Go fait exploser le dépôt et ne se « diffe » pas.

DVC garde dans Git un pointeur (hash + taille) et range le contenu dans un remote : dossier partagé, Azure Blob, GCS, S3.

DVC

Versionner un fichier

$ uv run dvc init --subdir
$ uv run dvc add data/raw/diabetes.csv
100% Adding... → data/raw/diabetes.csv.dvc créé, data/raw/.gitignore mis à jour
$ cat data/raw/diabetes.csv.dvc
outs: - md5: 9c4e8a… size: 23873 path: diabetes.csv
$ git add data/raw && git commit -m "Données brutes suivies par DVC"
$ uv run dvc remote add -d partage ../dvc-remote
$ uv run dvc push # et dvc pull sur une autre machine

Le fichier .dvc fait deux lignes utiles : Git le versionne, DVC retrouve le contenu correspondant dans le remote.

DVC

Le vrai gain : décrire le pipeline

Chaque étape déclare ses entrées, ses sorties et ses paramètres. DVC en déduit le graphe et sait quoi relancer.

DVC · projet fil rouge

dvc.yaml et params.yaml

stages:
  train:
    cmd: python -m diabetes_ml.train
    deps:
      - data/processed/train.csv
      - src/diabetes_ml/train.py
    params:
      - train
    outs:
      - models/model.joblib
  evaluate:
    metrics:
      - reports/metrics.json:
          cache: false
train:
  model: random_forest
  n_estimators: 200
  max_depth: 6

Changez max_depth, relancez dvc repro : seule l'étape train et ce qui en dépend se relancent.

DVC

Ce que fait dvc repro

CommandeRôle
uv run dvc reproexécute ce qui doit l'être, et seulement ça
uv run dvc dagaffiche le graphe des étapes
uv run dvc metrics show / diffles métriques, et leur évolution depuis le dernier commit
uv run dvc params diffquels paramètres ont changé
uv run dvc exp run --set-param train.max_depth=8une variante sans toucher aux fichiers

dvc.lock enregistre les hash des entrées et sorties : c'est lui qui sait si une étape est à jour. Il se commite.

Partie 5

MLflow : tracer et comparer les expériences

Chaque entraînement laisse une trace : paramètres, métriques, modèle.

MLflow

Dix entraînements plus tard…

$ ls models/
model.pkl
model_v2.pkl
model_v2_final.pkl
model_v2_final_OK.pkl
model_depth12_test_0.79_vraiment_final.pkl

Lequel avait 0,79 d'AUC ? Avec quels paramètres ? Sur quelles données ?

MLflow enregistre chaque exécution (run) dans une expérience : paramètres, métriques, artefacts, et le modèle lui-même.

MLflow

Les notions

Expérience

Un dossier de runs qui répondent à la même question : diabetes-risk.

Run

Une exécution : un identifiant unique, une date, un état, et tout ce qui suit.

Paramètres et métriques

log_params, log_metrics : ce qu'on a essayé, ce qu'on a obtenu.

Artefacts et modèle

Fichiers attachés au run : le modèle, un graphique, un rapport.

Registre

Un nom et une version pour le modèle qui part en production : diabetes-risk v3.

Tracking

Où tout cela est stocké : sqlite:///mlflow.db en local, un serveur partagé en équipe.

MLflow · projet fil rouge

Dans le code

import mlflow, mlflow.sklearn

mlflow.set_tracking_uri("sqlite:///mlflow.db")      # où stocker
mlflow.set_experiment("diabetes-risk")

with mlflow.start_run(run_name="random_forest") as run:
    mlflow.log_params({"n_estimators": 200, "max_depth": 6})
    pipe, metrics = fit(train_df, params)
    mlflow.log_metrics(metrics)                       # cv_accuracy, cv_roc_auc, …
    mlflow.sklearn.log_model(pipe, name="model", input_example=example)
    print(run.info.run_id)                            # identifiant unique du run

mlflow.sklearn.autolog() enregistre tout seul les hyperparamètres et métriques de scikit-learn. Pratique pour démarrer, moins lisible qu'un log explicite.

Dans le fil rouge, dvc repro relance train, qui crée un run : DVC orchestre, MLflow trace.

MLflow

Tracer, comparer, enregistrer, servir

uv run mlflow ui --backend-store-uri sqlite:///mlflow.db     # http://localhost:5000 : sélectionner des runs → Compare

MLflow

Le registre de modèles

Quand un run est bon, on lui donne un nom et une version. C'est ce nom que l'API ou le serveur chargera, pas un chemin de fichier.

uv run python -c "import mlflow; mlflow.set_tracking_uri('sqlite:///mlflow.db'); \
  print(mlflow.register_model('runs:/<RUN_ID>/model', 'diabetes-risk'))"

uv run mlflow models serve -m "models:/diabetes-risk/1" -p 5001 --no-conda

Le registre demande un backend base de données : sqlite:///mlflow.db suffit en local. Un simple dossier mlruns/ ne le supporte pas.

mlflow models serve donne une API de prédiction clé en main. En séance 2 nous écrirons la nôtre : plus lisible, plus légère, documentée.

DVC et MLflow

Concurrents ou complémentaires ?

DVCMLflow
Versionnefichiers (données, modèles) et pipelineexécutions (paramètres, métriques, artefacts)
Répond à« comment régénérer ce modèle ? »« quelle tentative était la meilleure ? »
Stockageremote : Blob, GCS, dossiertracking : sqlite, serveur ; registre
Dans le fil rougedvc repro orchestre les étapeschaque train crée un run

DVC rend l'exécution reproductible, MLflow la rend comparable. Beaucoup d'équipes n'utilisent que l'un des deux ; l'important est de couvrir les deux questions.

Ce qu'on retient de la séance 1

uv

pyproject.toml dit ce que vous voulez, uv.lock ce que vous avez, uv sync fait coïncider, uv run exécute dedans.

DVC

dvc add pour un fichier, dvc.yaml pour un pipeline, dvc repro pour régénérer ce qui a changé, push/pull pour partager.

Un run par entraînement, des paramètres et métriques explicites, l'interface pour comparer, le registre pour nommer le modèle qui part en production.

Trois fichiers de vérité : pyproject.toml + uv.lock (code), dvc.yaml + dvc.lock (pipeline), l'historique MLflow (expériences). Rien de lourd ni de secret dans Git.
